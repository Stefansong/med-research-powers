# Team Collaboration

## Overview

将研究任务分解为**互不依赖**的子任务，用子代理工具并行执行，主代理负责派发、审查和合并。
子代理只写各自的输出文件，不改共享文件；合并由主代理串行完成。

## When to Use

- 多个独立分析维度需要同时推进
- 系统综述需要同时检索多个数据库
- 4 位审稿人角色需要独立评审同一稿件
- 论文修回时多位审稿人的意见互相独立、数量大
- 需要多专业视角同时评审方案

## When NOT to Use

- 简单线性任务（一个 skill 就够）
- 任务之间有严格顺序依赖（必须先有 SAP 才能分析）
- 会跨越硬确认点（protocol / SAP / pre-submission）
- 用户偏好逐步确认每一步

## 子代理工具怎么用

Claude Code 的子代理工具名是 **Agent**（旧名 Task 仍可用作别名）。派发方式：**在同一条消息里并行发起
N 个 Agent 调用，每个带聚焦的 prompt**；它们会并行执行，主代理等全部返回后再合并。不要依赖任何具体的
参数签名——按当前会话的工具定义填写。

**每个子代理的 prompt 必须包含：**
1. 明确的角色定位
2. 具体的任务描述
3. 需要读取的输入文件（绝对路径或项目相对路径）
4. **只允许写入**的输出文件名（每个子代理不同）
5. 需要遵守的 SKILL.md / references 路径（用 `${CLAUDE_PLUGIN_ROOT}/skills/<skill>/...`）
6. 一句禁令："不要修改 manuscript/ 或其他共享文件"

## Auto-Parallel Rules（自动并行触发）

以下场景由主代理**自动**并行派发，无需用户确认：

| 触发时机 | 并行内容 | 理由 |
|---------|---------|------|
| `literature-synthesis` 进入执行检索且目标数据库 ≥ 2 | 每个数据库一个子代理同时检索（场景 1） | 数据库之间完全独立，无数据依赖 |
| `peer-review-simulation` 进入 Step 1（4-Reviewer Panel） | 4 个审稿人角色各一个子代理（场景 2） | 审稿人独立评审，天然并行 |

以下场景是**可选**的，由用户提出或主代理建议、用户同意后启动：

| 场景 | 并行内容 | 为什么要先确认 |
|------|---------|---------------|
| `revision-response` 意见量大且互相独立（场景 3） | 每位审稿人的意见由一个子代理起草回复和建议改动 | 不同审稿人可能要求改同一段落，主代理要串行合并 |
| `study-design` 完成后多专家评审（场景 4） | 统计 + 方法学 + AI 专家并行评审 protocol | 评审意见可能互相冲突，需要用户裁决 |

**建议话术：**
```
────────────────────────────────────────
💡 检测到可并行的独立子任务：

  • 子任务 A: [描述]
  • 子任务 B: [描述]
  • 子任务 C: [描述]

并行执行可以加速进度。是否启动？
────────────────────────────────────────
```

## Workflow

### Step 1: 识别可并行的子任务

主代理分析当前阶段，将任务分解为**互不依赖**的子任务。例如检索阶段：

```
主代理分析:
  "3 个数据库的检索互不依赖，输入相同（检索式），输出各自独立，可以并行"
  → 子任务 A: PubMed 检索 → pubmed-results.md
  → 子任务 B: arXiv 检索 → arxiv-results.md
  → 子任务 C: Cochrane 检索 → cochrane-results.md
```

**关键判断：** 只有"输入不依赖另一个子任务的输出、且输出文件互不相同"的任务才能并行。

### Step 2: 派发子代理

在同一条消息里并行发起 N 个 Agent 调用，每个带上面列出的 6 项内容。四个常用场景的 prompt 模板见
`references/parallel-scenarios.md`。

### Step 3: 等待 + 合并

主代理等待所有子代理完成，然后：
- 审查每个子代理的输出文件
- 检查输出之间的一致性（如：数字是否对得上、是否改了同一段落）
- **由主代理串行**合并到主项目文件（子代理不直接写共享文件）
- 生成 `team-collaboration-merge.md` 并向用户报告

## 场景模板

四个常用并行场景（① 并行文献检索 ② 多审稿人模拟 4-Reviewer Panel ③ 并行修稿 ④ 多专家方案评审）的
派发模板见 `references/parallel-scenarios.md`。每个场景都说明子代理各自的输出文件和主代理如何合并。

> 多审稿人模拟（场景 2）固定派发 **4 个子代理**：R1 方法学、R2 临床/领域、R3 学术编辑、R4 Devil's Advocate，
> 与 `peer-review-simulation` 的 4-Reviewer Panel 一致。

## 合并规则

| 情况 | 处理 |
|------|------|
| 子代理输出数字不一致 | 以分析脚本实际运行结果（`analysis-log.md`）为准 |
| 两个子代理建议修改同一段落 | 主代理逐段合并，冲突处向用户说明并决策 |
| 子代理发现需要另一个子代理的数据 | 停止并行，转为顺序执行 |
| 子代理改了不该改的文件 | 丢弃该改动，只取其指定输出文件；必要时重新派发 |
| 子代理完成质量不达标 | 主代理提供反馈，重新派发该子代理 |

## Output

主代理合并所有子代理的结果后生成 `team-collaboration-merge.md`，记录：每个子代理的任务与产出文件、
一致性检查结论（数字是否对得上、有无冲突）、合并到主项目的内容、以及给用户的报告。各子代理自身的
产出文件（如 `review-methods.md`、`pubmed-results.md`、`reviewer1-response.md`）由对应场景定义。

## Common Mistakes

| 想法 | 现实 |
|------|------|
| "所有任务都并行更快" | 有顺序依赖的任务并行会出错 |
| "子代理不需要详细 prompt" | prompt 越具体，输出越可控 |
| "让子代理直接改稿件省事" | 多个子代理写同一文件会互相覆盖；只能各写各的，主代理合并 |
| "并行完直接合并就行" | 必须检查输出一致性再合并 |
| "agent 越多越好" | 2-4 个最高效，过多增加协调成本 |

## Convergence

当以下条件满足时完成：
1. 所有子代理（Agent）已返回结果
2. 主代理已审查每个输出文件
3. 输出之间无不一致，无越权修改
4. `team-collaboration-merge.md` 已生成
5. 向用户报告合并结果

## Red Flags — STOP

- 任务之间存在顺序依赖却强行并行 → 停止，改为顺序执行
- 子代理产出数字互相矛盾 → 不得直接合并，以分析脚本实际运行结果为准后再合并
- 试图跨硬确认点（protocol / SAP / pre-submission）并行 → 阻止，必须先确认再继续
- 子代理 prompt 里没有指定唯一输出文件、或允许其改 `manuscript/` → 补上再派发

## 衔接规则

### 前置依赖
- 当前阶段必须已分解出**互不依赖**的子任务（无严格顺序依赖）

### 强制衔接
- `peer-review-simulation` 进入 4-Reviewer Panel → 自动用 Agent 并行派发 4 个审稿人子代理（场景 2）
- `literature-synthesis` 检索 ≥ 2 个数据库 → 自动用 Agent 每库一个子代理并行检索（场景 1）
- 并行完成后 → 回到主线，由调用方 skill 继续（本 skill 是辅助 skill，不更新 `.mrp-state.json`）

### 可选衔接
- `revision-response` 意见量大且互相独立 → 场景 3（需用户同意；子代理只写各自文件）
- `study-design` 完成后想要多专家评审 → 场景 4（需用户同意）
